# 设计文档：paper-conductor

日期：2026-05-22
作者：jiayou20021120-afk
状态：v0.2.0

## 问题

学术写作的 skill 生态越来越丰富（调研、写作、制图、去 AI 味、审稿、答辩 PPT），每个都很强但各自为战。写一篇论文时，你不想为每一步都手动切换工具，也不想每次都被踢去开另一个 skill。缺的是一个既能自己干、又知道何时叫更强工具的全程助手。

## 目标

1. 一个集大成的全程助手，覆盖论文生产的 8 个阶段。
2. 通用的写作、润色、基础审稿、路线规划，它自己直接做。
3. 遇到需要更强工具的环节（深度文献调研、框架图、中文 hard gate 去 AI 味、学校 DOCX 模板、多 reviewer 评审），推荐专门 skill 并交接。
4. 原创、MIT、独立发布，自己的写作/润色/审稿能力不内嵌任何外部 skill 的代码。

## 非目标（YAGNI）

- 不做 GUI。
- 不强行取代所有专门工具（需要专门引擎/外部工具/硬规则的环节，老老实实推荐更强的）。
- 首版只做中英双语触发，不做更多语言。

## 架构

纯文档型 skill（无脚本）。

```
paper-conductor/
├── SKILL.md              # 触发 + 两种模式 + 阶段表 + handoff 摘要
├── references/
│   ├── stage_cards.md    # 八阶段：自己做什么 + 何时升级
│   ├── handoff_protocol.md
│   └── swappable_skills.md  # 升级清单：何时换更强的专门 skill
├── examples/             # 中文毕业论文 / 英文期刊 两个全程走查
├── README.md
├── LICENSE               # MIT
└── .claude-plugin/
```

## 关键设计决策

1. **集大成 + 升级，不是纯导航。** 通用文本能力（写、润、审、规划）conductor 自己干；需要专门引擎、外部工具、或硬规则的环节，推荐更强的 skill 并交接。它既动手又动嘴。
2. **通用框架 + 默认升级栈。** 升级目标填公开 skill，用户可替换。
3. **自己的能力内置，升级目标只指向不内嵌。** conductor 的写作/润色/审稿靠自身 LLM 能力，不依赖外部 skill；推荐的专门 skill 不复制其源码，因此不受其 license 约束（ARS 是 CC-BY-NC，AWS 是 MIT），paper-conductor 自身干净 MIT。
4. **不变量规则。** handoff 每次显式列"不变量"（已核验数据、已定 RQ、术语表），给下游立护栏，防止数据被悄悄改写或编造。

## 版本修正记录

- **v0.1.0（初版，定位错误）：** 一开始把它设计成"只导航不执行"的纯调度层，明确写"不写作、不润色、不审稿、不制图"。这违背了项目本意（名字本来叫"论文润色器 大成版"，"大成"即集大成、什么都能干）。错误来源是过度追求"架构干净"和"防触发冲突"，把作者偏好的全能定位阉割成了空壳。
- **v0.2.0（本版，修正）：** 翻转为集大成助手。通用写作/润色/审稿自己干，专门环节升级。保留 8 阶段路由和 handoff 协议作为编排骨架。

## 与 ARS / AWS 的关系

paper-conductor 把 ARS、AWS 等当作各环节的"升级目标"。之前尝试把 AWS 合并进 ARS 上游被婉拒（维护负担），作者建议用 companion-plugin 模式。paper-conductor 是这个模式的实现：它自己能干大半，关键环节推荐这些更强的独立 skill，并在 README 大方致谢。
